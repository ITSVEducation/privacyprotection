# コア層・サービス層の不変条件と規約

CLAUDE.md には各不変条件の「主張」だけを1行ずつ置いてある。ここにはその**根拠**と
**検証方法**を書く。根拠を知らずに触ると、どれも「一見きれいなリファクタ」の形で退行する。

これらは `.claude/settings.json` の PostToolUse hook（`scripts/hooks/verify-privacy-invariants.ps1`）
で機械的に検証される。hook が失敗したら、テストを弱めるのではなく編集の方を直すこと。

## 検出の重なりは「トリム」であって「破棄」ではない

`core/spans.py` の `remaining_spans()`。`patterns.py` と `detector.py` の両方が使う。

優先度の低い検出が高い検出と**部分的に**重なり、かつ完全に包含されていない場合、その検出は
重なっていない残りの範囲に**切り詰められる**。破棄してはいけない。

破棄に退行させると実在の個人情報が黙って素通りする。典型例は、電話番号に隣接した住所が
まるごと落ちるケース。これはスタイル上の好みではなく**プライバシーバグ**として扱う。

## 検出範囲の算術: `Detection.text` は必ずスライスと一致する

`detection.text == original_text[detection.start:detection.end]` が常に成り立つこと。

正規表現の `.group()` をそのまま `text` に入れると、範囲をトリムした後に `start`/`end` と
食い違う。これは実際にバグを生んでいる。範囲計算を触ったら、その場でこの等式を検証する
アサーションをテストに足すこと。

## バッチ全体で `Masker` インスタンスは1つ

フォルダ一括処理では単一の `Masker` を使い回す。同じ実世界の値が常に同じトークン
（`【人名_1】` など）に対応することを保証するため。

インスタンスを分けると、ファイルごとに `【人名_1】` が別人を指す状態になり、対応表が
壊れて復元不能になる。既存のトークン風テキストとの衝突回避は `Masker.scan_existing_tokens()`
が担当する。

## `Restorer` は完全一致のみ

トークンの曖昧一致・自動補正を実装しないこと。壊れたトークンはそのまま残し、未知トークン
として報告する。推測で復元すると、AI 側で改変された文字列に対して**誤った実名を復元して
しまう**。誤りに気づけない形で個人情報が混入するのが最悪の失敗モードなので、
「復元できなかった」と言えることの方が価値が高い。

## 対応表 CSV は意図的に平文

`core/mapping_io.py`、`.pmap.csv`、UTF-8 BOM 付き。

脅威モデルは「クラウド AI に個人情報を渡さないこと」であって、保存時の暗号化ではない。
平文なのは手抜きではなく設計判断。読み込み時の重複トークン拒否は緩めないこと（重複を
許すと復元先が非決定になる）。

## レポート・エラーメッセージに検出値そのものを載せない

`services/` の処理後レポートに含めてよいのは、カテゴリ名・件数・ファイル名・トークン名だけ。
検出された実際の値は決して含めない。例外を作らない。

ログ・例外メッセージ・GUI のツールチップも同じ扱い。「デバッグのときだけ」も認めない
（そのまま残るため）。

## トークンのカテゴリラベルは閉じた語彙

`core/models.py` の `CATEGORY_LABELS` が唯一の定義元。複数の検出カテゴリが意図的に同じ
ラベルを共有している（`POSTAL` / `MYNUMBER` / `CREDITCARD` はすべて `番号` になる）。

新しいラベルを足す前に、既存のラベルで概念が足りているかを必ず確認すること。ラベルが
増えるとトークン形式が変わり、過去の `.pmap.csv` との互換性に影響する。
